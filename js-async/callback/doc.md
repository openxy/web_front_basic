# 回调接续

## 本版本引入的概念

**回调（callback）**：把「做完之后要做什么」写成函数、交给异步操作，做完它替你调用。`compute(onDone)` 里那个 `onDone` 就是回调——上一版的 `log('计算完成')` 被硬编码在函数里，这版换成了「调用方说了算」。

异步的连锁由此成为可能：任务 A 做完接 B，B 做完接 C。按钮改名「三连任务」，每个任务约 1 秒（`compute` 的忙等总长从 3 秒改成 1 秒），日志按 A、B、C 依序出现。

## 回调的账单：嵌套金字塔

三连任务写出来是这样——每一步的「下一步」都住在下一步的回调里：

```js
compute(() => {
    log('任务 A 完成');
    compute(() => {
        log('任务 B 完成');
        compute(() => log('任务 C 完成（三连结束）'));
    });
});
```

才三步就右移了两层，五步七步的链在旧代码库里真实存在（史称**回调地狱**）。账单不止缩进：每一步的错误处理要在**每一层各写一份**（`try/catch` 对异步回调无效，异常冒不出回调边界）；中间想调换 A、B 的顺序或跳过某步，要动的是整座金字塔的结构。

这不是写法不佳，是回调这个机制本身的极限——下一版换机制。

## 本版本的改动

忙等逻辑从点击处理里抽出为 `compute(onDone)`（总长 3 秒改 1 秒，供三连）；点击处理改为三层嵌套的回调链。

## 试试

1. 运行点「三连任务」：日志每约 1 秒出现一条，A→B→C——时钟全程在走
2. 数一数缩进层数；想象六连任务的形状，在纸上画一下
3. 把 B、C 两层对调（编辑模式）：要改几处、动几个嵌套层级？

## 思考题

- 为什么 `compute` 外面套 `try/catch` 拦不住将来某一步的异常？
- 如果 A、B、C 互不依赖（不需要接续），还该嵌套着写吗？（答案在最后一版）
