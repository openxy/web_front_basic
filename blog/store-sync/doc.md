# 本地存储

## 本版本引入的概念

存储层登场：新增 `lib/store.js`，用 **localStorage** 实现三个数据接口——`fetchResource`（读单条/全表）、`saveResource`（增改，无 id 自动分配自增 id）、`deleteResource`。键名 `post_1`、`comment_2` 按类型加 id 组织，模拟数据库按主键存取。`lib/data.js` 退居**种子数据**：首次加载播种一次，此后数据的生死都在 localStorage 里。

三拍：

+ **是什么**：一套稳定的读写契约（接口），一套可替换的介质（localStorage）。页面代码从此不直接碰数据文件，只认接口
+ **怎么兑现**：localStorage 的 API 天然同步——`setItem` 返回时数据已落盘，页面代码拿到返回值就能接着用，于是全站调用方零改动成本地「落库」（分层的红利：上一版后台的增删改只把内存操作换成 `saveResource/deleteResource`，界面一行不动）
+ **为什么**：上一版「刷新即失」的事故在这里翻案——刷新、关浏览器、明天再来，数据都在。代价是数据只活在这一台浏览器里：换台设备、换个浏览器就没有，也无法分享给他人——要共享就得连服务器，那是 v12 的事

两个旧账清偿：

+ **前台评论表单兑现**：v2 画好的表单，提交终于有去处——`submit` 事件拦下默认行为，`saveResource('comment', …)` 落库，就地重渲评论列表（匿名评论，front.md 的「允许匿名评论」到此闭环）
+ **排序口径**：存储层列表按 id 升序返回，「置顶优先、年代降序」这类业务排序留在调用方——接口管存取，业务管呈现，分工就这条线

## 与上一版的 diff

新增 `lib/store.js`；8 个页面各加一行 `<script src="…/store.js">` 并把数据读写换到接口上；`lib/view.js` 的两处数据访问同步换轨。界面上肉眼可见的变化只有前台评论真的能提交了。

## 观察

- 后台新建一篇诗文，回前台看得到；**刷新、关标签页、明天再开**——它还在
- F12 → Application → Local Storage：每篇诗文一个 `post_N` 键，值是 JSON 字符串——数据库的婴儿形态
- 删掉所有 `post_*` 键再刷新：种子数据回来了（`seed()` 的播种逻辑）

## 思考

+ localStorage 换成 sessionStorage 只差一个词，行为差在哪？哪些数据适合哪种寿命？
+ 接口是同步的（`fetchResource` 直接返回数据）。若介质换成网络请求，同步的调用姿势还成立吗？——v12 把这个问题变成全站的改造现场
