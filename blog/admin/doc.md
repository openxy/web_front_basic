# 后台管理

## 本版本引入的概念

前台之外立起后台：`/admin/` 三个页面——博文管理（表格列表：增删改、置顶、按标题搜索、按分类筛选）、新建/编辑表单、评论管理。**角色分野**由此成形：访客读前台，站长管后台（登录认证属于后端话题，本案例不做，见案例总览的边界说明）。

两个设计教学点：

+ **同一内容类型，两个站点模板**。后台复用 `DATA` 与模板库，但站点模板换了形（`renderAdminPage`：无侧栏、单栏工整、管理导航）——模板可多套，资源只有一份
+ **表单是接口的界面**。新建/编辑表单的字段一一对应 Post 的字段（标题、分类、标签、年代、摘要、正文、题解、出处、置顶）；校验分两层：HTML 原生校验（`required`、`maxlength`）先拦一道，JS 校验补自定义消息。`FormData` 一把读取，`split(/\s+/)` 把空格分隔的标签串拆成数组

CRUD 的实现此刻是**纯内存**的：`DATA.posts` 增删改、`renderTable` 重渲，删除与置顶按钮照样走事件委托（`e.target.closest('button')` 认领行内操作）。页脚那句「刷新即失」不是免责声明，是**此路不通**：数据活在页面生命周期里，导航一次就灰飞烟灭。上一版评论还是只读的，这一版后台能删，但读者在前台提交的评论依然无处可去——存储的缺位已成一课，v11 来补。

URL 侧后四条资源路由（`admin/posts/index|new|edit`、`admin/comments/index`）正是 Rails 七动作里 index / new / edit 三个「界面动作」的静态形态；create / update / destroy 三个「数据动作」等 v12 的真接口兑现。

## 与上一版的 diff

新增 `admin/` 四页；`lib/view.js` 追加后台模板组；`style.css` 追加表格与按钮样式；`sitemap.html` 补后台资源段。前台页面零改动。

## 观察

- 博文管理：搜「秋」只剩两篇；点置顶按钮，文字在「置顶/取消置顶」之间切换
- 新建一篇《秋词二首·其二》，保存后回前台列表页——它出现了；刷新一下——它消失了（内存之殇）
- 编辑表单的正文框：一行一句，与数据里的 `<p>` 段落互为镜像

## 思考

+ 删除一篇诗文后，它名下的评论成了孤儿（评论管理里显示「诗文已删」）——资源之间的关联（postId）该由谁维护？
+ 表单提交到哪里？`location.href = 'index.html'` 只是跳转，不是接口。对照 resource 的七动作表，缺的三个动作该长什么样？
