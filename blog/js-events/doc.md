# 事件与交互

## 本版本引入的概念

页面第一次对用户动作做出反应：列表页长出**筛选条**（分类/标签/排序三个下拉）与**分页器**，点选即变。首页同样从一次列全 8 篇改为每页 5 篇——同一个 `renderPager` 组件两处复用，打开首页就能看到页码。之前 `?category=诗` 只能从侧栏链接带来（URL 驱动），现在控件在页面里就能改（事件驱动）。

三拍：

+ **是什么**：事件是浏览器与脚本之间的交互契约——控件承诺「在某个时机，带一个事件对象来通知你」，脚本用 `addEventListener` 登记回应函数（监听器）。注册是声明式的：只登记不轮询
+ **怎么兑现**：单线程的 JS 主循环空转等待；用户点击/改变控件，事件对象进入队列，主循环取出执行对应监听器，监听器改状态、重渲列表，然后继续等待。`renderList` 只重写列表区域（`#post-toc`、`#pager`、摘要），站点外壳纹丝不动——事件驱动的增量更新，和 v8 的整页重渲形成对照
+ **为什么**：**事件委托**——页码按钮是动态生成的，给每个按钮挂监听器就得每次重渲后重挂；把监听器挂在按钮的容器 `#pager` 上，点击冒泡到容器时用 `e.target.dataset.page` 认领，按钮增删都不用重挂。委托以静制动，是列表类交互的标准姿势

**状态对象**（`state`：筛选条件 + 当前页）第一次登场：监听器只改 `state`，渲染只读 `state`——单向流动，「改状态 → 重渲染」的套路是 v13 SPA 路由切换的原型。

## 观察

- 列表页选「分类：文」：列表剩《陋室铭》一篇，分页器消失（不超过一页不显示）
- 筛选后翻页、再切排序：页码自动回到第 1 页（`state.page = 0`）——状态变化要考虑连带重置
- F12 控制台输入 `DATA.posts.push({id: 99, title: '测试', ...})` 再点筛选：动态列表对数据变化的响应方式一目了然

## 思考

+ 下拉框原生 `change` 事件和按钮 `click` 事件都注册在控件自己身上，为何只有页码按钮用了委托？
+ `state.category` 改变时 URL 里的 `?category=` 没有跟着变——刷新后回到 URL 参数的旧状态。要让「当前视图」可分享、可收藏，该怎么办？（这条线索在 v13 变成主角）
