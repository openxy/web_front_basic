
# 循环绑定的陷阱（此路不通）

## 本版本演示什么

**脚本化绑定的第一次尝试**：把行为从 HTML 搬进 JS——`querySelectorAll` 找到全部删除按钮，for 循环逐个绑 onclick。这是最直觉的写法，也是日常最常见的两个 bug 的来源。

## 此路不通：两个症状，一个根源

在线运行它，你会看到：

1. **点任何删除按钮，页面没反应**。打开控制台：`Cannot read properties of undefined (reading 'remove')`——`del(3)` 拿到的 3 越界了（页面只有三行，合法编号是 0、1、2）。
2. **「＋ 添加一行」新加的行，点删除无声无息**——连报错都没有。

根源拆开说：

- 症状 1 是 **var 闭包**：循环里绑的每个函数捕获的是**同一个** `i`（`var` 在整个函数里只有一个 `i`），循环结束它停在 3。点哪个按钮，调用的都是 `del(3)`。
- 症状 2 是**绑定时机**：循环只在页面加载时跑一次，当时的按钮集合里没有后来的行。行是动态的，绑定是一次性的——时机天然不匹配。

## 对照要点

- 与第一版相比：行为离开了 HTML，换来「必须自己找元素、自己管时机」的新责任
- 两个症状各有补丁（`let` 修症状 1、每次新增后重绑全部修症状 2），但都是追着症状跑；第三版换一个结构，一并消解

## 思考题

- 把 `var` 改成 `let`，症状 1 消失（每轮循环一个新的 `i`）。症状 2 为什么还在？
- 「每次新增行后重新跑一遍绑定循环」能同时修两个症状吗？代价是什么（对照第一版的三行，这里每次新增要做多少事）？
