# 动态事件

上一版做完了「点击即编辑」：td 与 input 靠 `replaceWith` 交替顶替，元素诞生时把事件挂上，替换后的白纸重新绑过。但流程里还埋着一个细节——本版只加一行代码把它钉死：`input.onblur = null`。概念只有一个：解绑。

## 本版本引入的概念

**解绑**：监听器不只会在元素离场时作废，也可以趁它还在场时主动摘掉。回车提交时 input 马上要被移出 DOM，而移除一个正握着焦点的元素会引发失焦，这次失焦又会再调一次 commitEdit——提交逻辑悄悄跑了两遍。提交前先把监听器摘干净，让本次提交确定是最后一次。

## 关键代码走读（index.html）

**commitEdit 里新增的一行**：`input.onblur = null`，位置在非空校验通过之后、`replaceWith` 之前。此刻 input 还握着焦点，马上要被移出文档；先摘掉监听器，随后移除引发的失焦就扑了空。这句不能挪到 `replaceWith` 之后——解绑是对还在场的元素做的手术，人走了就摘不着了。

**为什么只有回车路径需要它**：点别处提交时，失焦本身就是触发者，监听器执行完自然退场，不存在第二次；回车提交的触发者是 keydown，失焦还排在后面。解绑防的正是这条路径上的「身后事」。

**页面上看不出差别，恰恰是要点**：没有这一行，多出来的那次 commitEdit 作用在一个已不在文档里的 input 上——`replaceWith` 悄悄发生在文档之外，界面毫无异常。解绑不是修一个看得见的 bug，而是让「一次提交就是一次执行」成为确定的事实，不靠运气。

## 与上一版对照

| | 上一版（点击编辑） | 本版（解绑） |
|---|---|---|
| 改动量 | 三处绑定、两个新函数 | 一行：`input.onblur = null` |
| 回车提交之后 | 失焦会把 commitEdit 多调一次（无声无息） | 监听器已摘，提交即终点 |
| 事件观 | 元素诞生时把事件挂上 | 元素离场前把事件摘下 |

动态绑定管「生」，解绑管「死」：创建时挂上，离场前摘掉。至此，页面上每个监听器的生命周期都有头有尾，全程没有一环靠运气。

## 思考题

- 删掉 `input.onblur = null` 再回车提交，多出来的那次 commitEdit 作用在怎样的 input 上？页面上看得出异常吗？（提示：它已不在文档里，`replaceWith` 会悄悄发生在文档之外。）
- `onkeydown` 需要像 `onblur` 一样置 null 吗？input 被移出文档之后，keydown 还有机会触发吗？
- 正在编辑某格时直接点同一行的「删除」，事件按什么顺序发生？此时 onblur 还挂着，打了半截的字最终去了哪里？
