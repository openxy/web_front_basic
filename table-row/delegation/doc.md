# 事件委托

## 本版本引入的概念

**事件冒泡**：点击某元素，事件不只在它身上发生，还沿祖先一路上传（`a` → `td` → `tr` → `tbody` → …）。任何一层都能接住它。

**事件委托（delegation）**：反过来利用冒泡——监听器不挂在每个删除链接上，只挂一个在 `tbody`。行再多、来得再晚，点击总会冒泡到 tbody；`event.target` 是实际被点的元素，`closest('.remove')` 找到删除链接，`closest('tr')` 找到所属行。

## 本版本的改动

- 新增 tbody 委托监听器：`closest('.remove')` 甄别点击目标，是则 `closest('tr').remove()` 删行
- `addRow` 里的 `document.querySelector('tbody')` 提为顶部常量 `tbody`，两处共用

## 关键代码走读

- `if (!link) return`：点到数据单元格、表头都不是删除链接，`closest` 返回 null，直接返回——委托监听器必须自己甄别事件是不是冲自己来的
- `link.closest('tr').remove()`：行删自己，不问「我是第几行」——编号只是位置，不是身份。靠写死编号定位的写法在删除中间行后会错位，这里天然没有这个问题
- 删除逻辑一个字没写进 `addRow`：新增行不需要知道删除怎么实现，监听器先于一切行存在

## 对照要点（与逐个绑定的假想版对照）

| | 每个链接各绑一个 | 委托：tbody 一个 |
|---|---|---|
| 监听器数量 | 随行数增长 | 恒为 1 |
| 新增行 | 创建时必须记得绑，漏一处坏一处 | 天然被覆盖 |
| 绑定时机 | 必须踩准元素诞生时刻 | 不依赖时机 |
| 甄别成本 | 不需要 | `closest` + 早返回 |

- 逐个绑定的两个死穴（绑得早、绑漏了）在委托结构里失去发生的土壤——不是被修好，是不再可能发生
- 原课程的行内 onclick 其实也能覆盖新增行（属性随 HTML 字符串一起生成）；它的问题是行为散落在 HTML 里。委托把行为集中到一处，还顺便把「谁触发」的问题统一交给事件对象

## 思考题

- 若删除链接里嵌了一层 `<span>`（`<a><span>删</span></a>`），点击时 `event.target` 是谁？`closest` 为什么必要？
- 表格有 1000 行时，两种方案各有多少个监听器？内存与新增成本差在哪？
- 把监听器从 tbody 上移到 `table`、再上移到 `document.body`，功能还正常吗？上得越高越省事，为什么实际项目不建议一路挂到 document？
