
# 事件委托

## 本版本引入的概念

**事件冒泡**：点击某元素，事件不只在它身上发生，还沿祖先一路上传（`button` → `tr` → `tbody` → …）。任何一层都能接住它。

**事件委托（delegation）**：反过来利用冒泡——监听器不挂在每个按钮上，只挂一个在 `tbody`。行再多、来得再晚，点击总会冒泡到 tbody；`e.target` 是实际点击的元素，`closest('.del')` 找到删除按钮，`closest('tr')` 找到所属行。

## 对照要点（三版连看）

| | 行内 onclick | 循环绑定（失败分支） | 事件委托 |
|---|---|---|---|
| 监听器在哪 | 每行 HTML 属性里 | 每个按钮（一次性） | tbody 一个 |
| 动态新增行 | 随 HTML 一起生成 | 点了没反应 | 天然可用 |
| 删除依据 | 写死的编号 | 同一个闭包变量 | 行自身（`closest`） |
| 删中间行后再删 | 编号错位，删错行 | — | 无此问题 |

- 删除用 `closest('tr').remove()`：行删自己，不问「我是第几行」——编号只是位置，不是身份。第一版的暗病在此消失
- 监听器先于一切行存在，时机问题失去发生的土壤。第二版的两个症状不需要修，它们不再可能发生

## 思考题

- 表格有 1000 行时，三版各有多少个监听器？「每次新增后重绑全部」的方案贵在哪？
- 若按钮里嵌了一层 `<span>`（`<button><span>删</span></button>`），点击时 `e.target` 是谁？`closest` 为什么必要？
