# 加载更多事故

## 事故现场

依《事件传播》「事件委托」一节的两个动因之一改写：给运行时才诞生的元素绑事件，直接绑定会扑空。

观察步骤（运行本版）：

1. 初始八张图，点任意一张——高亮描边出现，正常
2. 点「加载更多」，追加三张新图
3. 再点新图（梯田/峡谷/湖泊）——没有任何反应，控制台也不报错

## 此路不通：症状与根源

- 症状：老图活着，新图死了——同一张页面、同一份 CSS、同一种元素，行为却分了两批
- 根源：`bindPicks()` 只在 `render()` 末尾跑过一次，逐个绑定覆盖的是「那一刻已存在」的元素。新图是之后 `insertAdjacentHTML` 追加的，诞生时没有任何人为它们挂监听
- 静默失败比报错更危险：不抛异常、不留日志，页面看着完好，交互悄悄丢了

## 本版本的改动

- 新增「加载更多」按钮：`pool` 三张备用图经 `insertAdjacentHTML` 追加到容器尾部
- 图片模板提为 `figHtml(p)`，初始渲染与追加共用（追加的图与老图长得一模一样，事故才成立）

## 关键代码走读

- 追加路径只有一行 DOM 插入，没有绑定调用——「元素诞生」与「接上行为」是两件事，直接绑定要求两件事在同一时刻发生
- 想修的话朴素办法是在追加之后再调一次 `bindPicks()`：能修好这页，但每追加一批就要记得重绑一批，漏一次就坏一次（下一版换结构，让这个「记得」失去存在的必要）

## 思考题

- 在追加后补调 `bindPicks()` 能修好新图，但老图会被绑上第二份监听吗？点一下老图看看高亮逻辑执行几次（可加 console.log 验证）。
- 如果 `pool` 清空后再点「加载更多」，会发生什么？这算 bug 吗？
