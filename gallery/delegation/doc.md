# 事件委托修复

## 本版本引入的概念

**事件委托**（依教程《事件传播》一篇，机制与取舍见教程）：监听器不再追着每张图跑，只挂在容器 `.gallery` 上一个。点击发生在图片上，事件沿祖先冒泡，容器接住；`event.target` 是实际被点的元素，`closest('figure')` 找到它所属的卡片。容器先于一切图片存在，晚来的图片照样冒泡——上一版「绑得早、绑漏了」的死穴失去发生的土壤。

## 本版本的改动

- 删 `bindPicks()` 及 `render()` 末尾对它的调用
- 新增容器级委托监听器：`closest('figure')` 甄别，非图点击早返回；高亮逻辑原样搬进监听器
- 「加载更多」处理与渲染函数一字未动——修复没有触碰出事的路径，出事的路径不再存在

## 关键代码走读

- `if (!fig) return`：委托监听器收到容器内的一切点击（图片、说明文字、格子间隙），必须自己甄别哪些冲自己来——这是委托与直接绑定唯一的额外成本
- `event.target` 可能是 `img`、也可能是 `figcaption`（点在标题文字上）——`closest` 从任意后代都能回到 figure，不挑点击落点
- 绑定与渲染彻底解耦：`render()` 只管拼 HTML，行为接续全部由容器监听器承担；追加多少批图都不需要「记得重绑」

## 对照要点（与上一版直接绑定对照）

| | 逐个直接绑定（上一版） | 委托：容器一个（本版） |
|---|---|---|
| 监听器数量 | 随图数增长 | 恒为 1 |
| 新增图 | 诞生时没人挂监听，静默失效 | 天然被覆盖 |
| 绑定时机 | 必须踩准元素诞生时刻 | 不依赖时机 |
| 甄别成本 | 不需要 | `closest` + 早返回 |

## 思考题

- 点在 `figcaption` 文字上，`event.target` 是谁？为什么照样能高亮？
- 把监听器从 `.gallery` 上移到 `document.body`，功能还正常吗？上得越高覆盖越广，为什么不建议一路挂到 body？（教程《事件传播》最佳实践同问）
- 1000 张图两种方案各多少个监听器？委托省的不只是内存——想想「追加一批图」时两种方案各要做几件事。
