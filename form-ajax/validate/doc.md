# 提交前校验

## 本版本引入的概念

**客户端校验**：格式问题（用户名合不合法、两次密码一致不一致）在浏览器里就能判，不必发上服务器走一遭。校验不过，fetch 根本不发出——「先校验、后请求」是表单提交的标准次序。

**行内提示**：错处标在出错的输入框旁边（`<span class="tip">` 红字），而不是弹一扇 alert 窗。alert 要用户点掉才能继续、一次只能报一个错、还挡不住「报完就忘」；行内提示留在原地，改了再提交即可。

## 本版本的改动

- 两个校验函数：`checkName`（正则：字母开头、只含字母数字）、`checkPwd`（非空且两次一致）
- `validate(data)`：规则表驱动，`[是否通过, 出错输入框, 提示文字]` 逐条写回各自 label 里的 tip
- 提交处理器开头加一道闸：不过即 return，请求不发出

## 关键代码走读

- 正则 `/^[a-zA-Z][a-zA-Z0-9]*$/` 对应原课程 PHP 端的 `preg_match('/^[a-z|A-Z][a-z0-9A-Z]+$/')`——注意原式字符组里混进了一个字面 `|`（`[a-z|A-Z]` 匹配竖线），重构时顺手修正；客户端校验只是体验优化，服务端校验永远是安全底线
- `input.closest('label').querySelector('.tip')`：从出错的输入框向上找到它的 label、再回到行内的提示位——DOM 就近定位，不给每个 tip 编号
- 规则表是数组不是 if 链：加第三条校验（比如密码长度）只需添一行，validate 的骨架不动
- 校验写回 tip 后，之前 blur 查重留下的绿字/红字（下一版）会被覆盖——提示位唯一，避免新旧两种说法叠在页面上

## 对照要点（与原课程 user_register.html）

- 原课程 `check_all()` 汇总两个 check 的 alert；本版规则表一次全部显示——用户一眼看全所有错处
- 原课程 `onsubmit='return check_all();'`（行内、返回 false 拦提交）；本版 addEventListener + preventDefault + 提前 return，同一道闸的现代写法
- 原课程手写 `is_valid_name` 逐字符判字母数字（还留了个正则版的 `is_valid_name2` 没用上）；本版直接用正则——它就是那版的转正

## 思考题

- 只做客户端校验、服务端不校验，攻击者会怎么绕过？（直接用 curl 发 POST——校验只是给守法用户的体验，安全永远在服务端）
- HTML5 的 `required` / `pattern` 属性能替代这些 JS 吗？（能拦「空」与「格式」，两个密码一致的跨字段逻辑不能——各自守住一层）
