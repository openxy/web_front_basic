# 闭包计数器

## 本版本引入的概念

**闭包（closure）**：函数记住自己出生时的作用域。`createCounter()` 里声明 `var n` 并返回一个函数——按常识 createCounter 执行完，n 该随调用栈销毁；但返回的函数攥着对 n 的引用，n 因此活在闭包里：外界无法直达它，函数内部却始终可用。

工厂天生配闭包：`createCounter()` 调两次就是两个独立计数器，各自一个 n，互不干扰——这是全局变量永远给不了的保证。上一版思考题的「开小口子」也在这里兑现：把「能改这个变量的函数」交出去，变量本身仍然私有。上一版的 IIFE 外壳顺手证明了自己就是一个闭包应用：包起来的变量靠暴露在外的接口活下来。

## 三个观察

1. 控制台敲 `n`：不存在——外界不可达
2. 连点三次：1、2、3——n 在两次调用之间活着（否则永远显示 1）
3. 教材上「函数 + 它捕获的环境 = 闭包」，在这里具体成：`next` 这个函数，和它的 n

## 本版本的改动

只改 counter.js：IIFE 内部改用 `createCounter` 工厂，返回的闭包函数接替裸变量 count；初始的 0 由 HTML 原文承担，按钮点击调 render → next()。timer.js 与 index.html 一字未动。

## 试试

1. 运行连点三次：1、2、3；刷新页面回 0——闭包活在页面生命周期里，不落盘
2. 编辑模式把 `createCounter()` 再调一次造出 `next2`、再挂一个按钮：两个计数器各数各的
3. 在控制台试着读或改 `n`：都做不到——私有性是真的

## 思考题

- 下一版里闭包会从工具变成陷阱——先想：如果用 `var i` 的循环生成三个函数，每个函数捕获的 i 是三个还是同一个？
- 闭包版的计数相比第一版的全局 count，谁更容易被别的代码误伤？
